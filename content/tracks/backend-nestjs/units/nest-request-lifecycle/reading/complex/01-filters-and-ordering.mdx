## The default error contract

Nest's built-in exception filter already turns `HttpException` and its subclasses into
responses:

```ts
throw new NotFoundException("order not found");
// 404 { statusCode: 404, message: "order not found", error: "Not Found" }
```

Anything *not* an `HttpException` becomes a generic **500** with the details hidden — which is
correct (never leak a stack trace or a driver error to a client) and is also why "my API
returns 500 for a duplicate email" happens: the driver error was never translated.

Translate at the boundary of the thing that produced it:

```ts
try {
  return await this.repo.insert(dto);
} catch (e) {
  if (isUniqueViolation(e)) throw new ConflictException("email already registered");
  throw e;                                  // unknown -> let it become a 500, and get logged
}
```

Rethrowing what you don't recognise is the whole discipline: map the **expected** condition,
never swallow the rest.

## A custom filter, and how selection works

```ts
@Catch(DomainError)
export class DomainErrorFilter implements ExceptionFilter {
  catch(error: DomainError, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();
    res.status(error.status).json({ code: error.code, message: error.message });
  }
}
```

- `@Catch(SomeError)` narrows what it handles; bare `@Catch()` catches everything.
- Nest picks **one** filter by position, not by how specific its `@Catch` is: it checks
  route-level filters, then controller-level, then global, and the first whose `@Catch`
  matches wins. So a route-level `@Catch()` beats a controller-level `@Catch(DomainError)`,
  even for a `DomainError`. (Within one `@UseFilters(A, B)`, `B` is tried first, which is why
  the docs say to list a catch-all first.)
- Filters don't chain: the chosen one owns the response. A catch-all must re-implement the
  default response shape or delegate to `BaseExceptionFilter`.
- A global filter registered with `useGlobalFilters(new X())` can't inject; use
  `{ provide: APP_FILTER, useClass: X }` when it needs a logger or config.

Filters own **presentation** of the error. They're not a substitute for handling errors where
the context is: a filter can't retry, and it can't know which of your three DB calls failed.
