`providers: [UsersService]` is shorthand for the full form:

```ts
{ provide: UsersService, useClass: UsersService }
```

Once you see the long form, the rest of the provider system is just choosing a **token** and
a **strategy**.

## Four strategies

```ts
@Module({
  providers: [
    UsersService,                                            // useClass shorthand
    { provide: "CLOCK", useValue: { now: () => new Date() } }, // a value/fake
    {
      provide: PaymentGateway,                               // swap the implementation
      useClass: process.env.NODE_ENV === "test" ? FakeGateway : StripeGateway,
    },
    {
      provide: "REDIS",                                      // needs async setup / other providers
      useFactory: async (config: ConfigService) => {
        const client = createClient({ url: config.get("REDIS_URL") });
        await client.connect();       // node-redis (v4 onward) doesn't connect on create — await it here
        return client;                // consumers get a client that's ready to use
      },
      inject: [ConfigService],
    },
  ],
})
export class InfraModule {}
```

`useFactory` is the escape hatch for anything you can't express as "call the constructor":
async connections, values that depend on config, one provider assembled from several others.
`inject` is positional — it feeds the factory's parameters in order.

## Interfaces can't be tokens

The injector reads *runtime* metadata, and TypeScript interfaces don't exist at runtime.
`constructor(private mailer: Mailer)` where `Mailer` is an `interface` gives you an
unresolvable dependency. Use a string/symbol token — declared once, next to the interface —
plus `@Inject`:

```ts
export const MAILER = Symbol("MAILER");
export interface Mailer { send(to: string, body: string): Promise<void> }

constructor(@Inject(MAILER) private readonly mailer: Mailer) {}
```

An abstract class works too, and keeps the type and the token as one symbol.

## Scopes: singleton is a decision, not a default you can ignore

| Scope | Instances | Use when |
| --- | --- | --- |
| `DEFAULT` | One per app | Almost always — services must be stateless |
| `REQUEST` | One per request | You need the request (tenant, user) inside a deep provider |
| `TRANSIENT` | One per consumer | Each injector wants its own copy (e.g. a scoped logger) |

Request scope is contagious — it bubbles *up* the injection chain:

```
(-> means "injects")
OrdersController  ->  OrdersService  ->  TenantContext   @Injectable({ scope: Scope.REQUEST })
per request now       per request now    per request
OrdersController  ->  PricingService                     still one instance: it never reaches TenantContext
```

Everything that depends on a request-scoped provider, directly or through others, is rebuilt
for every request, controller included; providers off that path stay singletons. That's a real
throughput cost, and it's why `AsyncLocalStorage` (or passing the value as an argument) often
beats `Scope.REQUEST` for "the current user/tenant". The opposite mistake — keeping the current
user in a field on a singleton — is the shared-state bug from the previous unit.
