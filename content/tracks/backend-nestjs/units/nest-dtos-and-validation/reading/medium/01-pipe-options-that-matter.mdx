title: The ValidationPipe options that change behaviour
---

```ts
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,              // strip properties with no decorator
    forbidNonWhitelisted: false,  // …or 400 instead of stripping
    transform: true,              // hand the handler a real DTO instance
    forbidUnknownValues: true,    // 400 on an object with no validation metadata (Nest defaults this to false)
  }),
);
```

## `whitelist` is a security control, not tidiness

Without it, extra keys survive into your handler. That matters the moment anything downstream
does a bulk assignment:

```ts
// body: { "email": "a@b.c", "role": "admin", "credits": 999999 }
await this.repo.update(id, dto);   // ❌ mass assignment: role/credits go straight through
```

`whitelist: true` deletes every property that has no validation decorator, so a DTO with only
`email` yields `{ email }`. The stricter `forbidNonWhitelisted: true` rejects the request
instead — better for internal APIs where an unknown field means the client is wrong, worse for
public APIs where you want forward compatibility.

## What `transform` does — and doesn't

Three distinct effects, easy to blur together:

- The handler receives an **instance of the DTO class**, not a plain object — so DTO methods
  and `class-transformer` `@Expose`/`@Type` behaviour work. (The pipe builds that instance to
  validate *either way*; `transform` only decides whether your handler gets it.)
- A **named** path or query param declared `number` or `boolean` is cast:
  `@Query("page") page: number` turns `"2"` into `2` — and `"abc"` into `NaN`, with no error.
  It's a cast, not a check.
- **Body DTO properties are not converted.** `{ "quantity": "3" }` against `@IsInt() quantity`
  is still a 400. A property converts only when it asks to: an explicit
  `@Type(() => Number)`, or `transformOptions: { enableImplicitConversion: true }` on the pipe.

Implicit conversion is convenient and surprising in two ways, both because it converts *before*
the validators run. A `boolean` property gets `Boolean(value)`, and `Boolean("false")` is
`true`. A `string` property turns `42` into `"42"`, so `@IsString()` stops catching numbers.
Prefer the explicit `@Type(() => Number)` on query DTOs, where the input genuinely is always a
string, and an explicit `@Transform` for booleans — `@Type(() => Boolean)` makes the same
`Boolean("false")` mistake.

## The status codes are part of the contract

- **400** — the body/params failed validation. `ValidationPipe` throws `BadRequestException`
  with a `message` array of human-readable failures. (Nest 12 adds `errorFormat: "grouped"`,
  which keys the messages by property path instead.)
- **422** — sometimes preferred for "syntactically fine, semantically invalid". Pick one and
  be consistent; Nest's default is 400.
- **500** — what you get when validation *didn't* happen and the handler blew up on
  `undefined`. A 500 on bad input is a missing-validation bug.

Return *all* failures, not the first one: a client fixing a form one field per round-trip is a
bad API. `class-validator` collects them; a hand-rolled validator has to be written to.

## Keep response shape separate from request shape

`CreateUserDto` and the user you return are different contracts — the response must never leak
`passwordHash`. Two options:

```ts
// class-transformer, applied by an interceptor
@Exclude() passwordHash: string;
// main.ts: app.useGlobalInterceptors(new ClassSerializerInterceptor(app.get(Reflector)));
```

…or an explicit `toResponse()`/mapper that builds the response object field by field. The
mapper is more code and impossible to get wrong by forgetting a decorator — which is why many
teams prefer it for anything sensitive.
