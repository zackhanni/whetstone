id: backfill-in-batches
title: Backfill in batches, not in one UPDATE
---

Step 3 of a rename, the obvious way:

```sql
UPDATE users SET display_name = fullname;   -- 50 million rows, one statement
```

One statement is one transaction, and on a big table that transaction is the problem:

- **Every row it updates stays locked until it commits.** A user who edits their profile during the
  20-minute backfill waits — or times out — on a row lock.
- **It's all or nothing.** Fail at minute 19 (a deploy restarts the connection, a constraint trips)
  and all 19 minutes roll back.
- **It writes a new version of every row at once**, which the table and its indexes carry until
  `VACUUM` reclaims the old versions, and which replicas must replay.

Instead, update a bounded slice per transaction and walk the table by primary key:

```sql
CREATE PROCEDURE backfill_display_name(batch_size int DEFAULT 10000)
LANGUAGE plpgsql AS $$
DECLARE
  last_id   bigint := 0;
  batch_max bigint;
BEGIN
  LOOP
    SELECT max(id) INTO batch_max
    FROM (SELECT id FROM users WHERE id > last_id ORDER BY id LIMIT batch_size) s;
    EXIT WHEN batch_max IS NULL;                -- walked off the end

    UPDATE users SET display_name = fullname
    WHERE id > last_id AND id <= batch_max
      AND display_name IS NULL;                 -- idempotent: skip rows already done

    last_id := batch_max;
    COMMIT;                                     -- each batch is its own transaction
  END LOOP;
END $$;

CALL backfill_display_name();
```

Why each piece:

- **Keyset over `id`** (the N+1 unit's pagination, applied to writes): each batch finds its range
  with an index scan, however far along it is. `OFFSET` would get slower every batch.
- **`COMMIT` inside the loop** releases each batch's row locks as soon as that batch is done.
  PL/pgSQL allows `COMMIT` in a procedure run by `CALL` (and in a `DO` block) — but only when it
  isn't already inside a transaction: wrapped in `BEGIN`, the `COMMIT` fails with
  `2D000 invalid transaction termination`. The same happens when the `CALL` is sent in one
  multi-statement query string (`CALL …; SELECT 1`), which PostgreSQL runs as one implicit
  transaction. If your migration tool wraps each migration in a transaction, or sends a file as one
  string, run the `CALL` as its own statement outside it.
- **`AND display_name IS NULL`** makes it safe to stop and re-run, and it doesn't overwrite values the
  new code already wrote.

The same loop works from application code — a script that runs one `UPDATE … WHERE id > $1 AND id <= $2`
per iteration in autocommit mode, perhaps with a short pause between batches so replicas and
`VACUUM` keep up. Tested on PostgreSQL 18 with 25,000 rows in batches of 10,000: three batches,
zero rows missed.
