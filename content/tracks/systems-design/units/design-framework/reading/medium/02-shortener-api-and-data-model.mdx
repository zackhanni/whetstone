title: The URL shortener, steps 3 and 4 — API and data model
---

The API is the functional requirements written as requests. (Which *style* — REST, RPC, gRPC —
is the HTTP track's [`rest-rpc-grpc`](/learn/http-and-apis/rest-rpc-grpc) unit; a public API that anyone calls from any language, plus a
redirect a browser follows, is resource-shaped HTTP's home ground.)

```http
POST /api/links
Content-Type: application/json
Idempotency-Key: 4f1c9a…

{ "url": "https://example.com/a/very/long/path", "expiresAt": null }

→ 201 Created
{ "code": "aZ3kP9q", "shortUrl": "https://sho.rt/aZ3kP9q" }
```

```http
GET /aZ3kP9q

→ 302 Found
Location: https://example.com/a/very/long/path
```

```http
GET /api/links/aZ3kP9q/stats

→ 200 OK
{ "clicks": 18234, "asOf": "2026-10-17T09:41:00Z" }
```

Three choices hide in there:

- **`Idempotency-Key` on create.** A client that times out and retries would otherwise mint two
  codes for one link. How the header works is the HTTP track's [`request-response-anatomy`](/learn/http-and-apis/request-response-anatomy);
  *why it's here* is the requirements: create is a POST, POST isn't idempotent, and mobile
  clients retry.
- **302, not 301.** The status code decides who may cache the redirect — and so whether you
  ever see a repeat click. The complex tier covers it.
- **`asOf` on stats.** The requirement said counts may lag, so the response says by how much
  instead of pretending to be live.

The data model follows the hottest operation. The redirect looks a link up by `code` and needs
only `long_url` and `expires_at`, so `code` is the primary key:

```sql
CREATE TABLE links (
  code        text PRIMARY KEY,           -- the redirect's only lookup
  long_url    text NOT NULL,
  owner_id    bigint,                     -- "my links" needs its own index on this
  created_at  timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz
);
```

Clicks are deliberately **not** a column the redirect bumps with
`UPDATE links SET clicks = clicks + 1`. At ~4,000 redirects a second that's thousands of row
writes a second, concentrated on the most popular links, where concurrent updates to one row
queue behind each other's row lock (the Databases track's [`transactions-and-isolation`](/learn/databases/transactions-and-isolation) unit) —
all on the path with the strictest latency budget. Instead the redirect publishes a click event
and returns; a consumer adds up counts per minute into a separate table. The trade is
freshness, which the requirements allowed, for a redirect that does one read and no writes.

<!--more-->

Most queues deliver at least once, so the consumer can see the same click event twice. For
analytics that tolerate a lag, a rare double count may be acceptable — but that's a decision to
state, not an accident to discover. If counts become billing, the consumer has to deduplicate by
event id (the NestJS track's [`nest-microservices-and-messaging`](/learn/backend-nestjs/nest-microservices-and-messaging) unit covers idempotent
handlers).
