title: How a server-only secret still reaches the browser
---

An unprefixed variable isn't inlined, but in Next.js 16 the server and the client share code and
pass data to each other. Three ways a secret crosses that boundary anyway:

**1. A server module imported into client code.** Modules can be imported from both sides, so a
helper written for the server can end up in a Client Component's import graph:

```ts
// lib/payments.ts
import "server-only";

export async function charge(amount: number) {
  return fetch("https://api.payments.example/charges", {
    method: "POST",
    headers: { Authorization: `Bearer ${process.env.PAYMENTS_SECRET_KEY}` },
    body: JSON.stringify({ amount }),
  });
}
```

Without the first line, importing `charge` into a `"use client"` file compiles; the secret isn't
inlined, so the call just fails in the browser. That's a confusing bug, and it's also server code
you never meant to ship. With `import "server-only"`, the docs promise "a build-time error" the
moment the module is imported into the client environment. Mark every module that touches
secrets, the database or internal APIs this way.

**2. Props from a Server Component to a Client Component.** Everything passed as a prop is
serialised into the page for the client:

```tsx
const user = await db.user.findUnique({ where: { id } }); // includes apiToken, passwordHash…
return <Profile user={user} />;                          // all of it is sent to the browser
```

The Next.js data security guide calls this out: pass only the fields the component renders (a
small DTO), not the database row.

**3. Server Action return values.** "Server Action return values are serialized and sent to the
client." Returning `db.user.update(...)` sends the whole updated record back, internal fields
included. Return what the UI needs: `{ success: true }`.

The guide's structural fix is a **Data Access Layer**: one `server-only` module that reads
`process.env`, talks to the database, checks authorisation and returns minimal objects. Everything
else imports from it. In its words: "only the Data Access Layer should access `process.env`."
When you audit, `process.env` outside that layer, and broad prop types on `"use client"`
components, are what to look for.

<!--more-->

React's taint APIs (`experimental_taintObjectReference`, `experimental_taintUniqueValue`, enabled
in Next.js with `experimental.taint`) stop a marked object or value from being passed to the
client. The guide calls this "an additional layer of protection" — filter the data in the DAL
first.
