---
id: a-leaked-secret-stays-leaked
title: A committed secret stays leaked — rotate first
---

You notice `PAYMENTS_SECRET_KEY=sk_live_…` in a commit from last week, already pushed. The
instinct is to delete the line and push. That fixes the file, not the leak.

**Why deleting isn't enough.** The value is in the commit that added it. GitHub's guide on removing
sensitive data lists where it stays reachable even after you rewrite history and force-push:
clones and forks, "cached views on GitHub" by commit SHA, and pull requests that reference it. You
can't reach into other people's clones. Anyone (or any bot scanning public pushes) who saw it has
it.

**So the order is:**

1. **Revoke or rotate the credential**, first and immediately. GitHub's guide: "as a first step
   you need to revoke and/or rotate that secret", and once that's done, the old value is worthless
   and history rewriting "may not be warranted". OWASP: "Keys that were exposed should undergo
   immediate revocation." Restarting your app changes nothing; OWASP: "Restarting the application
   does not itself revoke stolen credentials."
2. **Deploy the new value** to every environment that used the old one.
3. **Check what the old key did** while it was exposed: the provider's access logs, unexpected
   charges or API calls.
4. **Then decide about history.** If the repository is public, or the value can't be rotated,
   rewrite it with `git filter-repo` (GitHub's guide wants version 2.47 or later, for the
   `--sensitive-data-removal` flag), force-push, and have every collaborator re-clone. The rewrite
   changes commit hashes, removes signatures and is irreversible, which is why it comes last.
5. **Stop the next one**: secret scanning, a pre-commit hook, GitHub push protection.

**`NEXT_PUBLIC_` leaks are the same, only wider.** If a secret was ever built with the prefix,
it's in every JavaScript chunk that referenced it: on your CDN, in visitors' caches, in any copy
someone saved. Removing the prefix and redeploying stops new copies; only rotation makes the old
ones useless.

The same holds for secrets in logs, error-tracker breadcrumbs and screenshots in tickets: once a
value has been somewhere you don't control, treat it as public and rotate it.
