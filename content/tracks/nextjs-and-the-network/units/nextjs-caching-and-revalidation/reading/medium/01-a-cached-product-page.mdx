title: A cached product page with a personal cart, line by line
---

A product page every visitor shares, a cart badge that is different for each of them, and an
admin edit that must show up at once. Next.js 16, `cacheComponents: true`.

```ts
// lib/products.ts
import { cacheLife, cacheTag } from "next/cache";

export async function getProduct(id: string) {
  "use cache";
  cacheLife("days");
  cacheTag("products", `product-${id}`);
  return db.product.findUnique({ where: { id } });
}
```

```tsx
// app/products/[id]/page.tsx
import { Suspense } from "react";
import { cookies } from "next/headers";
import { notFound } from "next/navigation";
import { getProduct, getBestSellerIds } from "@/lib/products";

export async function generateStaticParams() {
  return (await getBestSellerIds()).map((id) => ({ id })); // prerender these at build
}

export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const product = await getProduct(id);
  if (!product) notFound();
  return (
    <main>
      <h1>{product.name}</h1>
      <Suspense fallback={<span>Cart…</span>}>
        <CartBadge />
      </Suspense>
    </main>
  );
}

async function CartBadge() {
  const cartId = (await cookies()).get("cart")?.value;
  if (!cartId) return <span>Cart (0)</span>;
  return <span>Cart ({await getCartCount(cartId)})</span>;
}
```

```ts
// app/admin/products/actions.ts
"use server";
import { updateTag } from "next/cache";

export async function renameProduct(id: string, name: string) {
  await requireAdmin(); // actions are public endpoints
  await db.product.update({ where: { id }, data: { name } });
  updateTag(`product-${id}`);
}
```

Why each piece is the way it is:

- **`generateStaticParams`.** Under Cache Components, `params` counts as request-time data unless
  at least one sample value is known at build. Listing the best sellers lets Next prerender those
  pages, and makes `await params` legal outside `<Suspense>`.
- **`"use cache"` on the data function, not the page.** The product is shared by everyone; the
  cart isn't. Caching at the data level lets one page mix both.
- **`id` is an argument, so it's in the cache key.** Each product gets its own entry. A value the
  function closes over from an outer scope would join the key too.
- **`cacheLife("days")`** makes the expected lifetime readable at the call site instead of
  inherited from the `default` profile (15-minute revalidate).
- **Two tags.** `product-${id}` invalidates one product; `products` invalidates every list and
  page that shows any product.
- **`cookies()` lives in `CartBadge`, outside any cached scope, inside `<Suspense>`.** A `use cache`
  function can't call `cookies()` or `headers()` (Next throws). Read them outside, and if a cached
  helper needs the value, pass it in as an argument, where it becomes part of the key.
- **`<Suspense>` around the badge** lets the shared part render ahead of time while the badge waits
  for the request. Without it, Next 16's build fails with a blocking-route error: runtime data
  (`cookies()`) was accessed outside of `<Suspense>`.
- **`updateTag` in the Server Action**, not `revalidateTag`: the admin expects to see the new name
  on the next render. `updateTag` expires the entry so the next read waits for fresh data.

<!--more-->

By default `use cache` stores entries in the server's memory. On a long-running `next start`
process they survive between requests; on serverless instances they often don't, so the docs
point to `'use cache: remote'` with a platform cache handler when a runtime cache must be shared
and durable. The prerendered shell itself is stored by the platform, which is the subject of
this unit's last reading.
