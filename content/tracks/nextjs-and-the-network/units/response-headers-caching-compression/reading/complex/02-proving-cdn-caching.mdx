---
id: proving-cdn-caching
title: Proving the CDN cached it — read x-vercel-cache, not Cache-Control
---

A Route Handler sends:

```http
Cache-Control: public, max-age=3600, s-maxage=3600, stale-while-revalidate=3600
```

On a local `next start`, `curl -sI` shows exactly that. On Vercel, the browser sees:

```http
Cache-Control: public, max-age=3600
```

Nothing is broken. Vercel's docs say that when `Cache-Control` is the only caching header, its
proxy **consumes** `s-maxage` and does not forward it, and it consumes `stale-while-revalidate`
(and `stale-if-error`) for all requests. Those directives were instructions for the CDN, and the
CDN followed them. What reaches the browser is what's left for the browser.

So "is my CDN caching in force?" can't be answered by reading `Cache-Control`. A check written
against a local build ("header must equal the route's value") passes locally and fails on Vercel
while the cache works. Ask the cache instead: request the URL **twice** and read the
`x-vercel-cache` response header.

```bash
curl -s -o /dev/null -D - https://your-app.vercel.app/api/catalog | grep -i x-vercel-cache
# x-vercel-cache: MISS     ← generated by your function, stored
curl -s -o /dev/null -D - https://your-app.vercel.app/api/catalog | grep -i x-vercel-cache
# x-vercel-cache: HIT      ← served from the CDN; the function didn't run
```

The values Vercel documents:

| `x-vercel-cache` | Meaning |
| --- | --- |
| `MISS` | Not in the cache; generated by your function or origin (and stored if cacheable) |
| `HIT` | Served from the cache |
| `STALE` | Served from the cache while Vercel refreshes it in the background |
| `PRERENDER` | Served from static storage, such as a page prerendered at build time |
| `REVALIDATED` | The entry had been deleted, so it was regenerated in the foreground |
| `BYPASS` | The cache was skipped on purpose (for example, Draft Mode) |

A second `MISS` means the response isn't being cached. Usual causes, from Vercel's cacheable
response criteria: no `s-maxage` (a function's response is cached only with one, or with a
CDN-targeted header below), `private`, `no-cache` or `no-store` on it, a `Set-Cookie` header, a
`Vary` on a near-unique header such as `Cookie`, or a different region answering the second
request (Vercel caches per region).

When you need the browser and the CDN to get different instructions on purpose, Vercel reads two
targeted headers before `Cache-Control`: `Vercel-CDN-Cache-Control` (Vercel only, top priority,
never forwarded) and `CDN-Cache-Control` (Vercel and any other CDN in the chain). With either one
set, Vercel forwards `Cache-Control` to the browser as is, `s-maxage` included.

<!--more-->

Each Vercel deployment starts with its own empty cache: the first request after a deploy is a
cold `MISS` even for a route that was a `HIT` five minutes earlier. Read cache behaviour some time
after the deploy, and read it on the platform. A local production build tells you what Next
emitted, not what the CDN in front of it did.
