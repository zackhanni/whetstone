title: Who calls this code? Four kinds of file in the App Router
---

In the Next.js 16 App Router, every file you write is one of four kinds, and the kind decides
**where it runs** and **who can call it**:

| Kind | Marked by | Runs | Called by |
| --- | --- | --- | --- |
| Server Component | nothing: the default for `page.tsx`, `layout.tsx` and what they import | only on the server, per request or ahead of time at build | Next.js, while it renders a route |
| Client Component | `'use client'` at the top of the file | on the server to prerender HTML, then in the browser | React in the browser (hydration, events) |
| Server Action | `'use server'` | on the server | the browser, over the network |
| Route Handler | `app/**/route.ts` exporting `GET`, `POST`… | on the server | anyone who has the URL |

One page uses three of them:

```tsx
// app/posts/[id]/page.tsx — Server Component: async, reads the database directly
import { getPost } from "@/data/posts";
import { LikeButton } from "./like-button";

export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const post = await getPost(id); // the query runs on the server and never ships to the browser
  return (
    <article>
      <h1>{post.title}</h1>
      <LikeButton postId={id} initialLikes={post.likes} />
    </article>
  );
}
```

```tsx
// app/posts/[id]/like-button.tsx — Client Component: state and a click handler
"use client";
import { useState } from "react";
import { likePost } from "./actions";

export function LikeButton({ postId, initialLikes }: { postId: string; initialLikes: number }) {
  const [likes, setLikes] = useState(initialLikes);
  return <button onClick={async () => setLikes(await likePost(postId))}>Like ({likes})</button>;
}
```

```ts
// app/posts/[id]/actions.ts — Server Action: the click becomes a network request
"use server";
export async function likePost(postId: string): Promise<number> {
  // check who is asking, write the like, return the new count
}
```

The split follows from what each environment has. A Server Component runs **once** to produce
output: there is no "later" on the server, so no `useState`, no `useEffect`, no `onClick`. In
exchange it can be `async`, `await` a query, and read secrets from `process.env`. Anything that
needs to react to the user lives behind `'use client'`.

`params` is a Promise: since Next 15 route params are async, and Next 16 removed the old
synchronous access.

<!--more-->

"Client Component" doesn't mean "skips the server". On the first load, Next renders Client
Components on the server too, to produce the HTML the browser shows before JavaScript arrives;
then React hydrates them in the browser. That is why the Data Security guide says Client
Components must follow the same security assumptions as browser code: their source ships to
everyone.
