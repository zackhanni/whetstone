## Cancel on unmount, or flush on unmount?

The version above **cancels** the pending save when the component unmounts — the last
edits are dropped. That's the safe default for a field that also commits on blur: clicking
a Close or Save button takes focus off the input first, so blur commits before the
unmount. If the field can be unmounted while focused — a modal closed with Esc, a route
change — you may want to **flush** instead.

The catch: an empty-dep cleanup closes over the **first** render's `text` and `commit`
forever. Since React 19.2, an Effect Event is the tool for reading the latest values from
an effect without making them dependencies:

```tsx
// React 19.2+
const flushPending = useEffectEvent(() => {
  if (!timer.current) return; // nothing was pending — the timer already saved it
  clearTimeout(timer.current);
  timer.current = undefined;
  commit(text); // the latest text and commit, not the first render's
});

useEffect(() => () => flushPending(), []); // the cleanup runs it on unmount
```

The cleanup is part of the Effect, so this keeps the rule that Effect Events are called only
from inside Effects (the `react-hooks` lint rule accepts it here, and rejects the same call
from `onBlur` — blur keeps calling `commit` directly). Two details carry the weight here:

- **Flush only when a save was genuinely pending.** `timer.current` is that flag — which
  only works if you set it to `undefined` when the timer fires *and* when you cancel.
  Otherwise unmount flushes a value the debounce already wrote.
- **Route the flush through the same `commit`** (the `lastCommitted` dedupe from the medium
  example). Belt and braces: even if the "pending?" check is wrong, the value can't be sent
  twice.

In development, StrictMode's extra mount cycle runs this cleanup once right after mount.
Nothing is pending then, so the guard makes it a no-op.

<!--more-->

Before React 19.2, the same job was done with a "latest values" ref, refreshed in an effect
after every commit — not assigned in the render body, which react.dev says not to do with
refs:

```tsx
const latest = useRef({ text, commit });
useEffect(() => {
  latest.current = { text, commit }; // declared before the cleanup effect below
});

useEffect(() => () => {
  if (!timer.current) return;
  clearTimeout(timer.current);
  timer.current = undefined;
  const { text, commit } = latest.current;
  commit(text);
}, []);
```

That's the pattern from the `useRef` unit's complex reading; `useEffectEvent` replaces it
when the reader is an effect.

> Flushing during unmount only works if `onCommit` doesn't need the component: a fetch or
> a store write is fine, a `setState` on the dying component does nothing.

## Debounced saves arrive out of order

Debouncing reduces the number of requests; it does not order them. Two saves 1.2s apart
can still land server-side in the wrong order if the first one is slow — and the older
text wins. Two fixes actually order the writes:

- Send a monotonically increasing revision/`updatedAt` with each write and let the server
  reject stale ones.
- Serialize: queue the next save until the current promise settles.

Aborting the previous request with an `AbortController` is not one of them on its own: it
stops the client waiting for the response, but a write the server already received can
still be applied after the newer one.

## Debounce vs throttle

- **Debounce** — run *once, after* the activity stops. Autosave, search-as-you-type,
  resize-settled. Risk: with continuous input it may never fire.
- **Throttle** — run *at most once per interval, during* the activity. Scroll position,
  drag handlers, progress pings. Risk: it fires while the value is still changing.

A "save at least every 5s while typing" requirement is debounce **with a max wait** — the
point where hand-rolling stops paying for itself and a tested utility (or a mutation
library that already coalesces writes) is the better answer.
