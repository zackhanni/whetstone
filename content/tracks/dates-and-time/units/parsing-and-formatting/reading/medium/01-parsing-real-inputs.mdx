title: Parsing what users and other systems actually send
---

Outside the ISO family, the spec lets each engine "fall back to any implementation-specific
heuristics". So `new Date("03/10/2026")` is a guess, and the guess is American:

```js
new Date("10/03/2026"); // V8 (Chrome, Node): October 3, 2026
// A UK user typed 10 March. Formatting can't fix a wrong parse.
```

MDN's advice is to make sure input conforms to the standard format, "because support for other
formats is not guaranteed". When you know the format, parse it yourself, into numbers:

```js
// A CSV from a UK client: DD/MM/YYYY
function parseUkDate(s) {
  const m = /^(\d{2})\/(\d{2})\/(\d{4})$/.exec(s);
  if (!m) throw new RangeError(`expected DD/MM/YYYY, got ${s}`);
  const [, dd, mm, yyyy] = m;
  return `${yyyy}-${mm}-${dd}`; // "2026-03-10": a date-only value, still unchecked
}
```

The regex only checks the shape: `31/02/2026` gets through. Checking that the date exists is
the next unit's job.

## Form inputs already give you ISO strings

- **`<input type="date">`**: `value` is always `"yyyy-mm-dd"`, whatever the display looks like
  (`10.03.2026` for a German user). That's a date-only string; keep it one. Its `valueAsDate`
  is a `Date` at **midnight UTC** (the HTML spec says so), so `input.valueAsDate.getDate()`
  shows the previous day anywhere west of UTC.
- **`<input type="datetime-local">`**: `value` is `"YYYY-MM-DDTHH:mm"`, with no zone. In the
  browser, `new Date(value)` reads it as the user's local time, which is usually what they meant.
  Convert there and send the instant:

```js
const instant = new Date(form.startsAt.value);  // in the browser: the user's zone
await save({ startsAt: instant.toISOString() }); // New York user: "2026-03-10T13:30:00.000Z"
```

Sending the raw `"2026-03-10T09:30"` instead makes the server parse it in **its** zone. MDN also
notes the control has no way to set a zone. If the time belongs to a different place than the
user's device (an event in another city), collect the zone separately and convert with it.

`new Date(value)` never refuses a time, even one the clock skipped. On March 8, 2026,
`"2026-03-08T02:30"` doesn't exist in New York and becomes 03:30; on November 1, `01:30` happens
twice and you get the first. For a booking or a reminder, check that the instant still reads back
as the time the user picked, and ask when it doesn't. The `date-only-and-dst` unit covers both.
