title: A poller that never overlaps, survives errors and stops cleanly
---

A status poller as you'd ship it. It polls once straight away, then again `intervalMs` after
each poll **finishes**, and `stop()` works whatever the loop happens to be doing.

```js
function pollStatus(onStatus, intervalMs = 5000) {
  let stopped = false;
  let timer; // the scheduled *next* poll, if there is one

  async function tick() {
    try {
      const res = await fetch("/api/status");
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      onStatus(await res.json());
    } catch (err) {
      console.warn("status poll failed", err); // report it, keep polling
    }
    if (stopped) return;                  // stop() ran while we were awaiting
    timer = setTimeout(tick, intervalMs); // only now schedule the next one
  }

  tick(); // first poll right away, not after 5 s

  return function stop() {
    stopped = true;
    clearTimeout(timer);
  };
}
```

Each line answers a specific failure:

- **`tick()` straight away.** `setInterval` and a first `setTimeout` both make the user wait a
  full interval for the first data.
- **Scheduling after the `await`.** The next poll can't start until this one has finished, so
  requests never overlap and never come back out of order.
- **`try`/`catch` around the work, with scheduling _outside_ it.** Without the catch, one failed
  `fetch` rejects `tick()`'s promise, which nobody handles: an unhandled rejection, and the
  `setTimeout` line is never reached. Polling stops forever and nothing tells you. Move the
  scheduling inside the `try` and the `catch` does report the error, but polling still stops.
- **Both a flag and `clearTimeout` in `stop()`.** When you call `stop()`, the loop is in one of
  two states:
  - _Waiting_, with a timer pending. `clearTimeout(timer)` cancels it.
  - _Working_, with a request in flight and no timer scheduled yet. There's nothing to clear, so
    without the flag the request finishes, schedules another tick, and the poller keeps going
    after you stopped it.

The handle and the flag cover different moments, and you need both. (`clearTimeout` on a timer
that already fired, or on `undefined`, does nothing, so calling it unconditionally is safe.)

<!--more-->

### Production refinements

- **Back off on failure.** Polling a failing server at full speed adds load at the worst
  moment. Track consecutive failures and stretch the delay, for example
  `Math.min(intervalMs * 2 ** failures, 60_000)`, resetting the count on success.
- **Cancel the in-flight request on `stop()`.** The flag stops the _next_ poll, but the current
  `fetch` still completes, and still calls `onStatus` after you've stopped. Check `stopped`
  before calling `onStatus` too, or pass an `AbortController`'s signal to `fetch` and abort it
  in `stop()`. The [Cancellation & races](/learn/async-javascript/cancellation-and-races) unit covers this.
- **Pause when nobody's looking.** Background tabs throttle timers anyway. Listen for
  `visibilitychange` and stop while `document.hidden`, then poll immediately when the tab comes
  back.
- **In a React component**, `stop` is what the effect's cleanup returns. That wiring is the
  [useEffect](/learn/react-hooks-and-rendering/use-effect) unit's topic.
