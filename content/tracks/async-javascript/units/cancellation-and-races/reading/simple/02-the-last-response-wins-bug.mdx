---
id: the-last-response-wins-bug
title: The last response wins, and it isn't always the last request
---

Search-as-you-type sends a request per (debounced) query. Requests are fast or slow for
reasons you don't control, so responses can come back in a different order from the one they
were sent in:

```
0 ms     search("r")     → slow, 900 ms
200 ms   search("rea")   → fast, 100 ms
300 ms   "rea" arrives   → shows results for "rea"   ✓
900 ms   "r" arrives     → shows results for "r"     ✗  the box still says "rea"
```

The code that causes it looks innocent:

```js
async function onQuery(query) {
  const results = await searchApi(query);
  render(results); // whichever response arrives last wins
}
```

It's a race, so it slips through testing on a fast local network and shows up for users on
mobile. Debouncing makes it rarer. It doesn't fix it, because debouncing controls when requests
start, not when they finish (the [`debounce-and-throttle-from-scratch`](/learn/async-javascript/debounce-and-throttle-from-scratch) unit).

There are two fixes, and they solve different halves of the problem:

**1. Abort the previous request.** It stops wasting bandwidth, and since the old request rejects
with `AbortError`, it never reaches `render`.

```js
let controller;
async function onQuery(query) {
  controller?.abort();                 // the previous query is now stale
  controller = new AbortController();
  // …fetch with controller.signal, and ignore its AbortError
}
```

**2. Only the latest request may write.** Tag each request, and drop any response that isn't
from the latest one:

```js
let latest = 0;
async function onQuery(query) {
  const id = ++latest;
  const results = await searchApi(query);
  if (id !== latest) return; // a newer query has started since: drop this
  render(results);
}
```

The id check works even when the request can't be cancelled: a third-party SDK, a cache, a
parse step after the response. Aborting saves the wasted work. Production code usually does
**both**, which is what the complex tier builds.

<!--more-->

### Same bug, other places

Autosave (an older save landing after a newer one), tabs that load data (switching tabs quickly),
and pagination (page 2's response after page 3's) are all "last response wins". The fix has the
same shape each time: cancel what's stale, and let only the newest result write. The [`use-effect`](/learn/react-hooks-and-rendering/use-effect)
unit shows the React version: an abort, or an `ignore` flag, in the effect's cleanup.
