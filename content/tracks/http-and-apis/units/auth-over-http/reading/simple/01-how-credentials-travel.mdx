title: Two ways to say who you are — a cookie session or a bearer token
---

HTTP is stateless: every request must carry its own proof of who sent it. There are two common
ways to do that, and they differ in **who attaches the proof** and **where the state lives**.

## A cookie session

```http
POST /login                                   (email + password in the body)

HTTP/1.1 204 No Content
Set-Cookie: sid=9f2c1e…; HttpOnly; Secure; SameSite=Lax; Path=/
```

```http
GET /me
Cookie: sid=9f2c1e…
```

- `sid` is a random, meaningless id. The server keeps a **session store** (a table, Redis):
  `9f2c1e… → { userId: "u_1", expiresAt: … }`, and looks it up on every request.
- The **browser** attaches the cookie by itself, to requests that match its domain, path and
  other attributes (the last example in this unit). Your JavaScript doesn't touch it (with
  `HttpOnly`, it can't).
- Logging out — or banning a user — is deleting the row. The next request fails immediately.

## A bearer access token

```http
POST /auth/login                              (email + password in the body)

HTTP/1.1 200 OK
Content-Type: application/json

{"accessToken":"eyJhbGciOi…","tokenType":"Bearer","expiresIn":900}
```

```http
GET /me
Authorization: Bearer eyJhbGciOi…
```

- The token is usually a **JWT**: the claims (`sub: "u_1"`, an expiry) are *inside* it, signed by
  the server. Verifying it is arithmetic on the token, no database lookup.
- **Your code** attaches the header, on every request, and decides where to keep the token
  between requests. "Bearer" means whoever holds the token is let in (RFC 6750) — like cash.
- It can't be cancelled early without adding a lookup back in. That's why access tokens are short
  (minutes), with a longer-lived refresh token to get new ones.

## Two separate choices

The token's **format** (opaque id or self-contained JWT) and its **transport** (cookie or
`Authorization` header) are independent. A JWT can ride in an `HttpOnly` cookie; an opaque id can
be sent as a bearer token. Browser apps lean on cookies because the browser attaches them for
you; CLIs, service-to-service calls and public APIs use the header, which every HTTP client can
set and which nothing sends unless your code does.
Which storage is *safer* in a browser is an attack-and-defence question — XSS and CSRF — and
belongs to the Web Security track.
