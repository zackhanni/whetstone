id: failure-modes
title: What each wrong choice actually costs you
---

Every misplacement has a recognizable symptom. Learn the symptoms and you can diagnose a
codebase in an afternoon.

## Context holding hot state

**Symptom:** the whole page re-renders on every keystroke/tick; `React.memo` on the
consumers changes nothing.

Context re-renders **all** consumers when the provider's value changes identity — there is
no per-field subscription, and memoizing the consumer can't help, because context updates
bypass the memo bail-out.

Be precise about which problem you have, because the fixes aren't interchangeable:

- **The value's *identity* churns but its contents don't** (a fresh `{ user, logout }` object
  every provider render). `useMemo` on the value is the fix — that's the
  `context-value-rerender` challenge from the previous unit.
- **The value itself genuinely changes often** (a draft string, a timer, a cursor position).
  `useMemo` cannot help you here: the value really is new, so every consumer really does
  re-render. Split one context into `StateContext` + `DispatchContext` so action-only
  consumers stop re-rendering, split the hot field into its own narrow context, or move it
  into a store with selectors — the only option that gives you per-field subscriptions.

## Server data copied into a client store

**Symptom:** "why is this list stale?" bugs, a `useEffect` that fetches and `setState`s,
and manual refresh buttons.

```tsx
// ❌ two sources of truth
const { data } = useQuery({ queryKey: ["orders"], queryFn: getOrders });
useEffect(() => { if (data) setOrders(data); }, [data]);   // now YOU own freshness
```

Keep the query as the source; put only the *client's* decisions (selected ids, filters) in
the store, and join them at render time. If you need an instant UI response to a write,
that's an optimistic update in the mutation — not a second copy in a store.

## Client state that should have been in the URL

**Symptom:** "send me a link to that filtered view" is impossible, and back/forward do the
wrong thing.

Filters, tabs, pagination, and the selected entity are navigation state. In the URL they
are shareable, bookmarkable, restorable, and get browser history for free.

## A store used for a single screen

**Symptom:** state that outlives the screen. You open the wizard again and it's still
half-filled; tests need a store reset between cases.

A module-level store is a singleton. That's a feature for app-wide state and a bug for
screen-local state — prefer local state (or a store created *per screen* and thrown away
with it). A flow that spans routes, like that wizard, can still use a store: create it in
the wizard's shared layout, or clear it when the flow finishes or is cancelled.

## SSR / hydration

**Symptom:** a hydration error in the console — React 19 reports "Hydration failed because
the server rendered text didn't match the client" (React 18 warned "Text content did not
match") — and the tree re-rendered from scratch on the client. If only an attribute differs
(a theme class), React 19 logs that the attributes didn't match and leaves the server's
value in place.

Anything read from `localStorage` (a persisted store, a theme) doesn't exist on the server.
Render the server's default, then apply the persisted value after mount — a hydration gate.
The cost that's left is a brief flash of the default. If that's unacceptable (a theme), the
server has to know the value up front, which means a cookie rather than `localStorage`, or
a small inline script has to apply it before the first paint.

Server state has the parallel version of this: prefetch on the server and hydrate the cache,
rather than fetching again on the client.
